Distributed Logistics & Warehouse Management System

A production-grade Java 21 microservices platform for end-to-end logistics operations — order fulfillment, inventory, shipment tracking, and real-time analytics.

Java 21 Spring Boot 3.2 Spring Cloud Gateway Apache Kafka PostgreSQL 16 Redis 7 Docker / Kubernetes AWS ECS · ECR · RDS · MSK

📦 System Overview

Eight independently deployable Spring Boot microservices expose REST APIs through a single Spring Cloud Gateway entry point and communicate asynchronously via Apache Kafka. All services share a PostgreSQL 16 instance in development (one schema per service domain) and Redis 7 for caching and token management.

API Gateway

Single entry point. JWT validation at edge, routing, circuit breakers, rate limiting.
Auth Service

Registration, login, JWT issuance & refresh, token blacklisting via Redis.

Shipment Service

Notification Service

🏗 Architecture

Pattern: Choreography-based Saga. No central orchestrator — each service reacts to Kafka events and publishes its own. A shared correlationId (UUID generated at order creation) ties all events together for distributed tracing.

Access token TTL: 1 hour   Refresh token TTL: 7 days
Claims: sub=userId, email, role, name   Signing: HMAC-SHA (JJWT)
Logout blacklist: Redis key "blacklist:<token>" with matching TTL
Refresh Token Rotation: Old refresh token revoked on use, new pair issued — prevents replay attacks.
Token Blacklist: Redis TTL mirrors remaining token validity — expired entries self-clean, no cron job needed.

🧠 Design Patterns Reference

Choreography Saga
order / inventory / shipment
Services react to Kafka events and publish their own — no central orchestrator. Loosely coupled, independently deployable.
Saga Compensation
inventory-service
On stock failure, releases partial reservations before publishing inventory-failed. Keeps data consistent without 2PC.
API Gateway Pattern
api-gateway
Single entry point — JWT validation once at the edge. Clients talk to one host regardless of internal service count.
Circuit Breaker
api-gateway (Resilience4j)
Sliding window (10 req), 50% failure threshold, 10s open state. Prevents cascading failures across services.
Token Relay
api-gateway → downstream
Decoded JWT claims forwarded as X-User-Id, X-User-Role headers. Downstream services trust these without re-validating.
Token Blacklist
auth-service → Redis
Revoked JWTs stored in Redis with natural expiry TTL. Stateless revocation — no per-request DB lookup.
Refresh Token Rotation
auth-service
Old refresh token revoked on use; new pair issued. Prevents replay attacks even if a token is intercepted.
Pessimistic Locking
inventory-service
findBySkuForUpdate() acquires row-level DB lock during reservation. Prevents overselling under concurrent order load.
Dead Letter Topic
Kafka — all services
*.DLT pattern. @RetryableTopic on inventory: 3 attempts, exponential backoff (1s, 2×), then DLT.
Read-through Cache
inventory / warehouse
@Cacheable (Redis) on hot reads. @CacheEvict on writes. Reduces DB load for frequently accessed reference data.
Materialized Read Model
analytics-service
Pre-aggregated daily rows built from Kafka events. Dashboard queries hit one table — no joins, no real-time aggregation.
Correlation ID
All services
UUID generated at order creation, propagated through every Kafka event. Enables end-to-end distributed tracing.
Schema-per-Service
PostgreSQL
7 schemas (auth, orders, inventory, shipments, warehouses, notifications, analytics) for logical isolation in shared Postgres.
Uniform Response Envelope
All REST endpoints
ApiResponse<T> wraps every response with success, message, data, timestamp — consistent contract across all services.

🎯 Interview Q&A Guide

Q: Walk me through the order fulfillment flow end to end.

Client POSTs → Gateway validates JWT, forwards to Order Service → Order Service saves Order(PENDING), generates correlationId, publishes order-created → Inventory Service picks it up, acquires pessimistic locks per SKU, reserves stock → publishes inventory-reserved → Shipment Service creates the shipment record; Order Service updates status — both in parallel → dispatch and delivery via REST calls publish further events that Notification and Analytics services passively consume.

Q: How do you handle distributed transactions without 2PC?

Choreography saga. Each service does a local DB transaction and publishes a Kafka event. If inventory fails, Inventory Service compensates (releases partial reservations) and publishes inventory-failed, which Order Service consumes to cancel the order. No 2PC, no global lock — each step is idempotent and reversible.

Q: How do you prevent overselling under concurrent load?

Pessimistic locking — findBySkuForUpdate() acquires a row-level DB lock per SKU during the reservation transaction. This serializes concurrent reservations for the same item. Redis caching is used for reads, but all writes go through the locked DB path.

Q: How does authentication work across services?

JWT validation happens once at the API Gateway edge. The gateway decodes the token, extracts userId and role, and forwards them as X-User-Id and X-User-Role headers. Services trust these headers — they never see external traffic directly. On logout, the access token goes into Redis with its remaining TTL. Refresh tokens rotate on every use and are stored in Postgres.

Q: What happens if a Kafka consumer fails?

Manual acknowledgment (AckMode.MANUAL) — consumers only call ack.acknowledge() after successful processing. The Inventory consumer uses @RetryableTopic: 3 attempts with exponential backoff (1s base, 2× multiplier). After all retries the message lands in the *.DLT dead-letter topic for manual inspection and replay.

Q: How does the analytics service scale under heavy order volume?

Pre-aggregated daily metric rows — one row per calendar day. Each Kafka event does a find-or-insert on the day's bucket and increments a counter. Dashboard queries are a simple date-range scan with no joins. This CQRS-style read model means analytical queries never touch the transactional services' databases.

Q: How do you trace a request across multiple services?

A correlationId (UUID) is generated at order creation and propagated through every Kafka event payload and as an X-Correlation-ID header. All services log it via MDC. Prometheus + Grafana provide metrics dashboards scraping all 8 /actuator/prometheus endpoints.

Q: Why choreography over orchestration?

Choreography keeps each service autonomous — no service knows about others, no single point of failure. The trade-off is flow visibility; we mitigate that with correlationId tracing and Kafka UI. For a well-defined saga like order → inventory → shipment, choreography is simpler and more scalable.

Q: Why schemas instead of separate DBs in dev?

All 7 domains are separate schemas within one PostgreSQL instance in dev — logical isolation without running 7 DB containers locally. In production, each service gets its own RDS Multi-AZ instance: physically isolated, independently scalable, separately backed up.
